# От описания пользователя к сценарию теста

Как превратить фразу вида «сделай тест, что игрок наполняет бочонок из ферментера и относит его гостю» в рабочий тест.

## 1. Разобраться, как механика устроена на самом деле

Ничего не угадывай: каждое имя, клавиша и поле должны быть подтверждены кодом или ассетом.

1. **Как задумано (GDD).** `Docs/GDD Dwarf Beer.md` — ищи по ключевым словам механики (`Grep`). Оттуда берётся «как играет человек»: какие клавиши, в каком порядке, что видит игрок. Если GDD расходится с кодом, верь коду (тест проверяет игру), но назови расхождение в отчёте.
2. **Как реализовано (C++).** `Source/MonsterPotion/*`: компонент или актор механики, его `UFUNCTION`, реплицируемые поля (`DOREPLIFETIME`), условия, при которых действие отказывает (`return false/nullptr` в начале функции — это и есть правила механики: «котёл не берёт дрова при готовом сусле»), откуда вызывается (`NetworkGrabSyncComponent` — E/ЛКМ; `BeerInventoryComponent` — руки, G, колесо, 1–0).
3. **Blueprint-часть.** `scripts/dump-assets.ps1 -Paths <пакеты>` → `Saved/AssetDumps/*.txt`: переменные (точные имена, GUID-суффиксы у структур), компоненты (имена частей: `WortIntake`, `LoadingStairs`, `Tap`), графы, StateTree. Для карты — `-Filter <часть имени класса>`: где что стоит.
4. **Уже готовое в тестах.** `Source/MPFunctionalTests` — может, нужный шаг уже есть (`AddPourBeerAndTakeIt`, `AddTakeOrder`…). Переиспользуй, не дублируй.
5. **Если валидных способов несколько** (сбросить G с помоста или бросить с зарядом с земли) и из GDD неясно — спроси пользователя один раз, предложив вариант по умолчанию. Если пользователь просил работать автономно — выбери, запиши в «принятые решения».

## 2. Выбрать вид теста

| Нужно проверить | Вид | База / где |
|---|---|---|
| Одна механика, один игрок, изолированно | Функциональный тест на пустой карте, фикстура спавнится | `AMPFunctionalTest` / `AMPBrewingTestBase` / `AMPTavernTestBase`, `MPFT_*.h/.cpp` |
| Механика в реальном окружении (навмеш, раскладка, родные станции и гости) | Функциональный тест на копии карты | то же, `--map-copy`, `BindLevelStation/BindLevelTavern`, `AddNavGoTo` |
| Несколько игроков, без проверки сети | Локальный кооп (split-screen) | `AMPFT_TavernCoop` как образец: `AddLane`, роли |
| Сеть / репликация / RPC клиента / лаг | Сетевой CQTest | `MPNetTavernCoopTest.cpp` + `AMPNetCoopPlayer` (см. `network.md`) |
| «Как живые игроки» на долгом отрезке | Смена с доской задач | `ShiftWorker` в `AMPNetCoopPlayer`, `FMPShiftBoard` |
| Дизайн-метрика (дальность, время, количество) | Тест метрики: значение берётся из игры и сравнивается с ожиданием из дизайна | отдельный тест; ожидание — параметр с комментарием-ссылкой на GDD |

Если сомневаешься — начинай с одного игрока на пустой карте: быстро, детерминированно. Сеть и смена — поверх работающего одиночного сценария.

## 3. Разложить на действия игрока

Пиши сценарий как текст «что делает человек», каждая строка = один шаг с именем в стиле `"<Объект>: <действие> (<клавиша>)"`:

```
1. Подойти к ферментеру со стороны крана              -> AddGoTo / AddNavGoTo + AddApproach(Fermenter)
2. Нажать E — кружка в руках                           -> AddKeyClick(E) + AddWaitUntil(в руках пиво)
3. Отнести гостю и подать (ЛКМ)                        -> AddApproach(Guest) + AddClickOn(LMB, Guest, руки пусты)
4. Гость доволен                                       -> Check(OrderResult.Success)
```

Соответствие «действие → хелпер»:

| Действие игрока | Хелпер |
|---|---|
| Дойти куда-то на пустой карте | `AddGoTo` (станция) / `AddWalkTo` / `AddWalkPath` |
| Дойти по реальной карте | `AddNavGoTo` (или `AddGoTo` в level-режиме), точка — `NavPointNear(Цель, Дист, MustSee)` |
| Подойти, чтобы взаимодействовать | `AddApproach` / `AddApproachComponent` (случайная дистанция в пределах дальности игры) |
| Взять / положить / подать (ЛКМ), взаимодействовать (E) | `AddClickOn(Name, Key, Target, Done)` — с прицелом, повтором, следованием |
| Нажать клавишу без цели (Space, G, E на себя) | `AddKeyClick` / `AddClickUntil` |
| Бросить предмет в отверстие | `AddDropInto(Opening, Done, ReadyToDrop)` |
| Забраться на блоки/помост | `AddClimbTo(FindStepsUpTo(Цель) + Цель)` |
| Ждать игру | `AddWaitUntil(условие на состоянии)`, `AddWaitUntilSettled` |
| Проверить | `AddAction(..., Check(...))` |
| Решение «что делать дальше» во время игры | `QueueTask` / `AbandonTask` (см. смену) |

## 4. Решить, что проверять

- **Результат по состоянию игры**, а не по «шаг дошёл»: тип и признак готовности предмета (`UPotionIdentityComponent`), счётчики станции (`GetReadyWortBuckets`, `GetReadyServings`, `GetLoadedWortBuckets`), монеты `BrewDirector->GetSharedCoins()`, репутация (`Reputation`), состояние гостя (`GuestStateOf`).
- **Точные ожидания там, где они точны** (`монеты == было + номинал`), «не меньше» — где параллельно действуют другие игроки (`>=`).
- **Побочные эффекты-баги**: заспавненное не в игроке (`AddWatchSpawnedClearOfPlayer`), игрока не подбросило, предмет не провалился.
- **В сети**: читать на клиенте только реплицируемое. Теги актора не реплицируются! В конце — сверка снимка состояния сервер/клиенты.
- Каждый `Check` с текстом, в котором есть увиденные значения: `"Coins %d, expected %d + %d"`.

## 5. Числа и таймауты

- Дистанции — от `GetGrabReach()`; количества — из компонентов игры (`GetRequiredWortBuckets()`), не литералами.
- Таймаут шага — с запасом ×2–3 к нормальному времени (с рендером всё медленнее; в сети — пинг). `TimeLimit` теста — сумма с запасом.
- Ожидание долгого процесса (брожение, варка) — через параметр в Details (`FermentTimeout`), не литерал в шаге.
- Случайность: всё случайное — через `Random` (сид прогона), никаких `FMath::Rand`.

## 6. Ловушки, о которых думать заранее

- Трасса взаимодействия идёт из камеры игрока: камера должна быть на пешке (`bKeepViewOnPlayer`), цель — видимой точкой поверхности.
- Предмет в руках раскачивает камеру; клики во время анимации рук игнорируются → `AddClickOn` (повтор), а не одиночный клик.
- Физические предметы катятся: ищи их заново перед подходом, жди `Settled`.
- Отверстия (котёл, ферментер) принимают только упавшее внутрь; крышка/зона загрузки — условие `ReadyToDrop`.
- На реальной карте: навмеш не ведёт на помосты и станции; напарники и гости стоят в проходах; предметы на клиентах могут проваливаться.
- Blueprint-менеджеры, которые «ищут друг друга в BeginPlay», не увидят заспавненное тестом позже — выставь ссылку рефлексией.
- Всё, что игра пишет в лог как Warning/Error, валит тест: заранее смотри лог первого прогона.
Полный список — раздел 7 `Docs/Technical Design/Functional Tests.md`.

## 7. Несколько игроков

- Одна дорожка на игрока; координация — через состояние игры (`AddWaitUntil` на котле/ферментере), а «разговоры» (что варить) — через общее поле теста или доску.
- Фиксированные роли — для проверки конкретного взаимодействия; доска задач — для «живой» нагрузки.
- Всё параллельное ломается на гонках: «один уже взял», «ферментер наполнился, пока нёс», «котёл перестал принимать». Каждое «перед действием» — проверка, что действие ещё имеет смысл; если нет — `AbandonTask("почему")`.
- Ожидания «ровно N» заменяй на «не меньше» / «на одно больше, чем до моего действия» (`LoadedBeforeDrop + 1`), и проверяй, что именно мой предмет ушёл из рук.
